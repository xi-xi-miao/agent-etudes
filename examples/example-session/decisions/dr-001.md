# DR-001 — How to test two placed parts for overlap

*Synthetic fixture, part of the example session (example / c001 / attempt 1).*

- **Date / timestamp:** +0:26 (revisited at +1:47, held)
- **Status:** decided

## Decision

Test overlap with **pairwise exact polygon intersection** — Shapely polygons with
holes, an STRtree bounding-box pre-filter, and `intersection.area <= TOL_AREA`
as the accept test — and spend the rest of the session on the placement
heuristic instead of on the geometry layer.

## Options considered

| Option | For | Against |
|---|---|---|
| A — No-fit polygon (NFP) | The right answer for this problem family; makes "slide part B along part A until it touches" a direct computation, so the placement heuristic gets much stronger; what the nesting literature assumes | I had never heard of an NFP two hours earlier; correct NFP construction for concave parts with holes is genuinely hard and degenerate cases bite; a broken NFP produces invalid layouts that look plausible |
| B — Pairwise exact intersection | Two lines of Shapely I can read and trust; the validator uses the same predicate, so my accept test and the official one cannot drift apart; fails loudly, never silently | O(n²) pairs per candidate placement; no help at all in *choosing* where to put a part, only in rejecting bad choices |
| C — Raster masks | Very fast overlap test; trivially handles holes | Resolution artifacts either allow hairline overlaps the validator rejects or waste material; a second geometry representation to keep in sync with the exact one |

Option A came from the challenge README's background pointers and from the
`TUTOR` explanation. B and C came from the agent when I asked for alternatives.
The field narrowed to these three because the agent argued — and I checked —
that everything else in this space reduces to one of them.

## Confidence

**3 / 5** at the time of deciding. I was confident the pairwise test would be
*correct* and not at all confident it would be *enough* — I knew I was trading
away the placement quality that an NFP would have unlocked, and I could not
estimate how much.

## Outcome

Held, and it was the right call for a first attempt in an unfamiliar domain: the
geometry layer never produced a single invalid layout, and every bug I chased
lived in the placement heuristic where I could actually see it. The cost is
visible in the measure — utilization stalled in the low fifties, barely above
the shelf-packing floor, because rejecting bad placements is not the same as
finding good ones.

Same call again for attempt 1. For attempt 2 I would keep the pairwise
intersection as the *oracle* — it is cheap insurance and it agrees with the
validator — and build an NFP alongside it purely to generate candidate
placements, with the exact test as the referee whenever the two disagree. What I
would want to know first: how the standard NFP construction degrades on parts
with holes, which is exactly the question I did not know how to ask at +0:26.
